# ADR 0001 — 工会（GuildDisplay）滚轮支持判定为 NO-GO

- 状态：**已被 v11 重评取代**（原 NO-GO 于 2026-11-13 12:50 接受；17:48 用户明确要求
  「继续解决工会页面的问题」后重新派发 `p25-*` 三路调研 + `p26-*` 独立对抗审核，
  判定 GO 有条件，进入实验性实现）。**下文保留原始 NO-GO 论证作为历史记录**，
  但「无注入点」这一核心理由已被推翻，请以本文件末尾的「v11 重评」节为准。
- 影响范围：`ScrollWheel` 插件；不改变已实机验收的出征补给 / 地牢背包滚轮行为
- 取证材料：`build/scrollwheel/p22-guild-research-a.md`、`p22-guild-research-b.md`、
  `p23-guild-adversarial-review.md`；基准 exe SHA1
  `9db2d73b89aa034e2055df65a139403e18df641f`，ImageBase `0x140000000`，地址均为 RVA

## 决策

**不实现工会技能栏滚轮。** `guild` 配置键保留仅为兼容旧配置，**恒不生效**；
DLL 不写 `0x2B8EBAC`，不安装任何工会相关 hook，不捕获 GuildDisplay 实例。
文档、cfg 注释、启动 WARN 统一改为「明确不支持」，删除所有「留待 SackScroll 重做 /
next stage」的措辞。

## 背景与约束

原始需求是给工会、出征补给、地牢背包补滚轮。补给/背包已通过「事件泵 cave → 16ms
tick → 写布局数组 `[2] start_y`」实机验收；v10 又用 `r8` 面板 gate + `param_5` 行号
只裁上界，已实机通过。工会是唯一未达成项。

用户明确约束（不可违反）：

1. 不采用 SDL2 代理注入（SackScroll 1.2 用 `SDL_PollEvent` / `SDL_GL_SwapWindow`
   转发；我们已有 DLL 加载器）。
2. 不自绘任何 UI / 滚动条（v7、v8 两次实机翻车，v9 起彻底移除）。
3. 不破坏已实机验收的补给 / 背包滚轮。
4. 任何改动必须可一键回退。

## 失败史（实机证据）

- v6 每 16ms 写 `0x2B8EBAC`（所有英雄共享的 skill_pos.y 起始 Y，行高
  `0x2B8EBB4 = 91`）→ 不同技能数的英雄网格与名字横幅错位。v8 起停止注入。
- `0x6837C0` 计算 `Y = start_y + 91*i` 并快照进 `HeroSlot+0x68`；该值是绘制期的
  每帧读者 `0x7F5ED8`（`UI::Panel::Base::Show` 的局部 translate）所读的字段。

## 证据链（含对抗审核更正）

两路静态调研给出 NO-GO；独立对抗审核**主动尝试推翻**后仍判定 NO-GO 成立，
但更正了若干论证错误。以下为最终采信的版本：

### 对抗审核更正（不得再沿用旧论证）

1. **真正的限制不是「坐标数据源分裂导致必然只移动子集」**（旧结论有指令级错误），
   而是 **`+0x100` 扁平 vector 无技能区专属父容器**。改 GuildDisplay 自身 `+0x68`
   实际上会通过祖先 translate **一次性带动整棵 widget 树**（技能图标 + 名字横幅 +
   英雄信息 + 标题/按钮/背景），所以「只滚技能栏、横幅不动」在静态上做不到。
2. `+0x260` 并非「无法确证」：`0x4086B0` 工厂用 qword `mov`（非浮点指令）从
   `.data` 全局 `0x2B8EB08/0x2B8EB10` 加载，故早期扫 `movss` 找不到。
3. `Base::Show` 每帧调用**静态可确证**，不是「频率无法确证」；任何基于它的 cave
   必须按「每帧、全 UI 共用」评估性能与重入。
4. 「捕获 GuildDisplay 实例」与「遍历 `+0x270` 逐槽写 `+0x68`」是两个独立步骤：
   前者（`0x4086B0` 工厂返回 / `0x66E9F0` slot23 / `0x7F5D90` 入口）**零竞态**，
   不得把后者的 realloc/撕裂/覆盖风险算到前者头上。审核至少找到 3 个零竞态捕获点。
5. `0x691360` 证明同族 slot42 回调**可以每帧调用**；「`0x6837C0` 事件驱动、
   100% 非每帧」应标为「[推测，有 v6 实机错位旁证]」，**静态不可确证 ≠ 运行时不可能**。
6. 「证伪 / 无法」一律限定为「在当前 exe + 四条约束下静态未发现」。
7. 布局全引用表漏了 9 条 `lea` rip 引用（`0x62291F / 0x6328A9 / 0x63292E /
   0x639863 / 0x6398A8 / 0x689AAC / 0x689C13 / 0x689C2A / 0x68AD79`，指向
   `guild_upgrade_tree_layout` `0x2B8EB88/90/98`）；不影响 `0x2B8EBAC` 结论，
   但「全部引用」措辞不实。

### 被审核否决的可行候选

`0x7F5EDD` cave 临时偏移栈上 `[rsp+0x54]`、调用后恢复，技术上可做到「整棵 widget
树统一平移 + 零残留 + 不碰已验收路径」，配合 `0x4086B0` / `[rcx]==0x140EBB8D8`
白名单可零竞态捕获实例。**但仍不构成可交付实现**，因为：

- 只能整个工会面板平移（含标题/按钮/背景），不是用户要的「技能栏滚动」；
- 无裁剪 ⇒ 重现 v10 刚修好的「滚出去的物品画到城镇背景上遮挡视线」；
- 命中矩形 / tooltip 是否取同一矩阵栈静态未确证（`0x274ca0` / `0x27bae0` /
  `0x272790` 待实机），点击/悬停可能错位；
- 违反约束 3/4 的风险域（每帧、全 UI 共用的通用函数）。

## 备选方案与拒绝理由

| 方案 | 拒绝理由 |
| --- | --- |
| 每 16ms 写 `0x2B8EBAC` | v6 实机已证伪：英雄网格与横幅错位 |
| 遍历 `+0x270` 逐槽写 `HeroSlot+0x68` | realloc 竞态、撕裂、被 `0x6837C0` 覆盖、头槽 `+0x288` 漏处理；且横幅/热点不动 |
| detour 网格函数截断数据源（SackScroll 式） | 工会根本不走 `0x7E9F80` / `0x7EADE0`；SackScroll 自身也不支持工会 |

| 整个工会面板平移（`Base::Show` cave） | 见上「被审核否决的可行候选」；需放宽约束并补实机证据 |

## 后果

- **正面**：补给 / 背包滚轮 + v10 无外溢裁剪保持已实机验收状态，零新增风险；
  不再有误导性的「下一阶段重做工会」承诺；`guild` 键语义明确。
- **负面**：原始需求三项中工会一项永久未达成，须在交付说明中如实告知用户。
- **配置**：用户真实 cfg 为 `provision=1 / guild=1 / raid_inventory=1 /
  clip_out_of_window=1`；模板为 `0/0/0`。两套值分开写清，`guild=1` 恒不生效。

## v11 重评（2026-11-13 18:00，本节取代上面的 NO-GO 决策）

用户明确要求继续攻坚工会，等于放宽「零误伤必须静态证明」这条前提，
接受「误伤面可枚举、可诊断、可一键回退 + 单独实机验收」。

**被推翻的结论**：三路 `p25` 调研 + `p26` 对抗审核独立复核后确证：

1. `[GuildDisplay+0x270]` **就是只包住技能槽的容器**（元素 vtable 为技能槽类型），
   `+0x100` 与它存同批指针 ⇒ 用「每帧刷新的指针表」可以只匹配技能槽，
   不需要「技能区专属父 widget」。旧结论「只能整个面板一起动」不成立。
2. `Base::Show` 的 `0x7F5EDD`（**6 字节**，p22/p23 写的 7B 是错的）可只改栈上
   `[rsp+0x54]`，零残留、不写任何对象/全局、不怕 `0x6837C0` 重算覆盖。
3. **绘制 / 命中 / tooltip 同源已静态闭环确证**（`p25-b`）：`0x26C3F0` →
   `0x274CA0 GUI_AppendWidget` 快照矩阵 → `0x273800` 重放 →
   `0x273600` 逆变换做命中测试；建槽时未快照绝对坐标。p23 §四的未决项解除。
4. 名字横幅/标题不跟随**不是缺陷，正是技能栏滚动的期望行为**；
   v6 的真正问题是共享常量 `0x2B8EBAC` 被每帧写导致英雄间采样不一致，
   而 v11 根本不写它。
5. 旧方案「一次性缓存指针表」确会因 `0x682B90` 切英雄 clear+析构而悬垂，
   但改为 **`0x66E9F0` 每帧刷新表** 即消除；审核 S1/S2/S3 已给出三条硬约束并落实。

**新决策（GO 有条件 → 已实现 v11，实验性、默认关闭、待实机验收）**：

- 新增独立键 `guild_scroll`（代码/模板默认 `0`，用户 cfg 显式 `1`）；
  `0` 时两个工会 cave 一个都不装，新增校验也不执行，v10 四个已验收 cave 不受影响。
- hook A `0x66E9F0`：每帧判 GuildDisplay vtable，刷新技能槽指针 + 原始 Y。
- hook B `0x7F5EDD`：命中表且工会活跃时，给 `xmm1` 加该槽本帧增量后重放 stolen；
  滚出上沿的槽用**有限**屏幕外值 `-100000.f` 一起移出绘制/命中/tooltip。
- 独立状态机 + 单点输入路由；`max = clamp((N-R)*rowH, 0, cap)`，
  行高取运行时槽 Y 相邻差（禁硬编码 91）。
- `p26` 三条必须先修全部落实：cave 内零 `call`（时间用 tick 侧原子计数）、
  stub 沿用 `GridEntryAsm` 契约（push/pop 平衡、重放 stolen、FF25）、
  校验/锚点/PrepareCave 整体包在 `if(guildScroll)` 内且失败不 `return`。

**仍诚实保留**：开启态「零误伤」静态不可证明（外溢用移出屏幕而非不产生
widget 参数条目、可见行数静态无法确证、`Base::Show` 是全 UI 每帧共用函数），
v11 **未经实机验收**。验收清单与一键回退见 `ScrollWheel/README.md` §8.4。

## v11 实机证伪与 v11.1 修正（2026-11-13 19:32~19:45）

**v11 首次实机：工会滚轮不生效**。116 条 `[DIAG]` 里 `gBeat/gN/gCur/gHit/gClip`
恒 0，而 `guildY=-40` 持续 35 秒（工会确实打开）、`qWrite=6 storeY 20→-8.59→20`
（滚轮确实进了 DLL，但被路由到补给状态机）。⇒ 唯一断点是**技能槽表从未刷新**。

复核后确认：**判据常量 `0x140EBB8D8` 没错**（`0x408758` 工厂 / `0x6827D4` 构造
两处 `lea` 精确写入该 vptr，已固化成离线单测断言），错的是上文第 5 条所依赖的
前提——「`0x66E9F0` 每帧必经」。该函数地址出现在 **18 个 `.rdata` 虚表槽**，
是 `BuildingDisplay` 基类共有函数；静态的 `7F5F06 call [rax+0xb8]` 只证明有调用点，
不证明 GuildDisplay 运行时会走这条 `Base::Show` 分支。实机 `gBeat=0` 直接证伪。

**v11.1 修正**：把刷新并入 `0x7F5EDD`（`Base::Show` 每帧必经、`0x7F5ED8` 读 widget
`+0x68` 的位置）——遇到 GuildDisplay 本体时自己读 `+0x270` 刷表，时序早于
`0x7F607A` 的子 widget 递归 Show；`0x66E9F0` 降级为备用 + 诊断。两个 cave 新增
`callsA/callsB/seenB/lastVtA/lastVtB` 五个自检字段，使「cave 没执行」与「判据没命中」
在日志里可区分。**这是 p28 产物审核未能覆盖的一类问题：机器码全对，但所依赖的
游戏函数在运行时根本没被调用；只能靠实机 DIAG，而 v11 的 DIAG 恰好缺执行计数。**

证据：`build/scrollwheel/p29-v11-guild-failure-diagnosis.md`（⚠️ 该文件结论已被 P30 推翻，文件头有更正）。

## v11.2 终局修正：ASLR 与补给面板门控（2026-11-13 19:48~19:58）

**P29 的「链没执行」结论是错的**。v11.1 的自检计数反证：`gACalls=258`、
`gBCalls=196565`，两个 cave 每帧都在执行；`gSeenB` 恒 0 的原因是 **ASLR**：

```
gVtA = 7FF7D8C8B8D8                     ← hook A 读到的真实 vptr
gVtA - 0xEBB8D8 = 0x7FF7D7DD0000       ← 64K 对齐的实际模块基址
cave 里硬编码 = 0x140EBB8D8             ← PE 磁盘 ImageBase 下的值，永不相等
```

`0x408758` / `0x6827D4` 的 `lea rax,[rip+…]` 是 RIP 相对的，**静态算出来是磁盘 VA，
运行时却是 `g_base + RVA`**。此前所有静态复核（含单测断言）验证的是「常量来源」，
不是「运行时值」；p26 甚至把 `movabs rax, imm64` 误标为「ASLR 安全」。

**修复**：`GuildTable.expectedVptr` 由 C++ 写 `g_base + kGuildVtableRva`，
两个 cave 用 `mov rax,[r11+0x438]` 读它比较，**cave 不再内嵌任何 exe 绝对 VA**。
`kGuildVtable`（磁盘 VA）保留但标注「仅离线断言」。

**同时修复另一个实机问题**：`Wheel::Tick` 的 `layoutHit` 硬编码 `true` 且
`WriteOffset` 每帧无条件写三套布局 ⇒ 在城镇/工会滚滚轮会改写补给 `start_y`，
之后打开补给商店已被翻页。新增 `gate_wheel_by_panel`（默认 1）按
`active != 0 || cells > 0` + 480ms 宽限窗口门控滚轮与布局写入，`0` 可回退 v10。

**方法论教训（写进决策，防止第四次重犯）**：
1. 凡涉及 exe 地址的运行时判据，**必须**用 `g_base + RVA`，不能内嵌 PE 磁盘 VA。
2. 静态反汇编「常量来源正确」≠「运行时能匹配」；涉及 ASLR 的假设必须靠实机 DIAG 里
   **记录真实运行时值**来验证，而不是靠 capsone/单测断言。
3. 每个 cave 都要有**无条件执行计数**，否则「诊断字段全 0」无法区分
   「cave 没跑」与「判据没命中」——v11/v11.1 连续两轮误判都源于此。
4. 把某个信号（`layoutHit`）从「由 hook 提供」改成「恒 true」时，必须重新审计
   它对**非目标界面**的副作用；v10 验收只覆盖了目标界面内的正向路径。

证据：`build/scrollwheel/p30-v112-aslr-and-panel-gate.md`。

- **工会滚轮 ✅ 用户实机确认通过**（20:15：「工会翻页完全生效了」）。
  实机观察是最终判据，据此将工会滚轮**记作已验收**。

**保留一条已知诊断缺口**：本次 109 条 DIAG 中 `gSeenB/gN/gActive/gHit/gBeat` 全 0，
与实机生效不一致。20:15 复核排除了环境性解释（游戏目录仅 1 份 DLL `95f80f3d…`、
仅 1 份日志且无轮换、cfg `guild_scroll=1`），判定为 **DLL 侧工会 DIAG 统计未覆盖
实际生效路径**的可观测性问题，**不是功能缺陷**。若将来复核，可在工会 cave 里加
无条件计数并记录原始指针。证据见 `build/scrollwheel/p31-v112-acceptance-and-closeout.md` §3。

**最终交付形态**：补给 / 背包 / 工会滚轮 + 补给面板门控，三项均已实机验收通过；
`guild_scroll = 0` 仍可随时完全关闭两个工会 cave（一键回退）。
